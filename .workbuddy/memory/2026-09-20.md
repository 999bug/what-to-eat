### 关键结论（供后续接续）

1. **技术路线选 PWA（方案 D），不重写**。理由：核心动作只有「抽一个结果 + 记一条记录」，**零依赖原生能力**（无相机/GPS/推送/支付）。RN/Flutter 重写成本约 4–6 倍且要过审；Capacitor 套壳比 PWA 更贵（$99/年 + 签名 + 提审）但内核仍是 WebView。
2. **唯一值得转原生的触发条件是「推送通知」**（饭点提醒），次要是「上架流量」「健康数据同步」。若要推送，路径是 D → Capacitor 只补推送插件，**不重写 UI**。
3. **实测体检数据（生产构建 390×844 @2x）**：JS gzip **83.7 KB**、CSS gzip **3.2 KB**、JS 原始 268 KB、**logo.png 243 KB（占全站 74%，须压缩到 ≤12 KB）**。→ **性能不是瓶颈，问题在交互与原生质感。**
4. **实测发现的移动端问题（10 条，P1–P10）**：顶栏「不知道吃什么就交给它 · 9…」在 390px **被裁切**；页面约 3 屏导致 **CTA 沉底**（违反 PRD「≤3 次点击」）；菜系 12 个 chip 横向滚动；滑动到转盘后**看不见已选条件**；结果卡用全屏居中模态**遮挡转盘**断掉动线；**夜宵仅 18 道候选**；无 manifest/SW；无触觉与手势；安全区未实测。
   （注：曾怀疑「水煮蛋」食材数据穿帮，**复核后确认源码 `'鸡蛋'` 是正确的，那是我原型 mock 的误植**，不存在数据 bug。）
5. **餐次候选数实测**：早餐 41 / 午餐 136 / 晚餐 128 / **夜宵 18**。夜宵 7 天降权后极易重复，建议夜宵档位把降权窗口从 7 天放宽到 3 天。
6. **改造要点**：餐次改吸顶分段控件、菜系筛选进底部抽屉（消除横向滚动与滑动手势冲突）、转盘吃满剩余高度、**CTA 固定底部**、结果改**底部 Sheet**（转盘露一半）、全元素 active `scale(.97)`、热区 ≥44px、`theme` 默认改 `auto`（原为 `'light'`）。
7. **可复用分层与口径零改动**：`data → lib(date/pool/stats/storage) → stores → components` 直接复用。
8. **持久化补充**：iOS Safari 在存储压力下会清 localStorage，建议补 `navigator.storage.persist()`。

## 结果面板「看不清」修复 + 全局三级文字对比度审计（2026-09-20，已完成）

三级文字 `--text-3` 是全站最弱的一环，**大面积不达 AA**：

| 主题 | 原值 | surface | surface-2 | bg | 判定 |

### 修复

1. **token 提对比度**：light `--text-3: #9a8f82 → #786d60`（worst 4.26）、dark `#8a8078 → #9c9288`（worst 4.64），均过 AA。

### 测试写法的坑（值得记）

`tests/customStore.test.ts` 最初 5 个用例挂在同一个原因上：
**不要 `candidates.find(菜名)` 然后断言存在。** `candidates` 是 `pickCandidates()` 从约 800 道内置菜里
按权重随机抽 8 个出来的，新加的菜大概率不在这一次抽里 → `find()` 返回 `undefined` → 后续 `addRecord(dish!)` 崩在 `dish.kcalKnown`。
这不是代码 bug，是测试押在了随机数上。

两种正确写法（已写进 `docs/PROGRESS.md` §3，避免后来人再踩）：

1. **断言属性** → 直接 `customToDish(customDishes.find(...))`。走的是 `currentPool()` 里喂给 `poolForMeal` 的**同一条转换路径**，既确定又仍有覆盖价值。
2. **断言「能进池」** → 循环 `refreshCandidates()` 60 次看是否出现过；或直接断言 `poolForMeal()` 的返回结果。

顺带把「忌口能挡住自定义菜」也改用循环刷新 + 反向断言（60 轮都不许出现），比单次断言更狠也更稳。

### npm 卡死根因（本机重要坑，跨项目适用）

- **宿主级代理 `127.0.0.1:10974` 只在沙箱内可用**：沙箱外 npm 继承该代理变量，首个 metadata 请求无限挂起（零输出、无 socket、连 boot 日志都停在第 2 行）。修复：`env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy node npm-cli.js ...`（沙箱外跑，真机 fs 速度）。
- **强杀 npm 留下半解压包**：目录在、package.json 在，但 dist 被掏空（vite-plugin-pwa、@rollup/plugin-babel 等 16 个）。校验脚本按 lockfile 逐包核对「package.json + 版本一致 + main/module 入口文件存在」（只查顶层条目数会漏掉壳包；只查任一入口存在会漏掉 CJS 被掏空），损坏的 `curl --noproxy '*'` 拉 tarball（校验 sha512）+ `tar --strip-components=1` 全新解压，绕开 npm reify 的 EPERM 换入死锁（Windows Defender 文件锁是元凶）。
- 结论：本机 npm 重操作 = 沙箱外 + 清代理 env + prefer-offline；修复损坏树用脚本精确重装，不要反复 npm ci。
