# 竞品调研报告 —「今天吃什么」随机选菜 + 三餐记录类产品

调研日期：2026-09-20　调研方式：公开搜索（小程序 / App / 开源 Web 项目 / 饮食记录类产品）

---

## 一、市场现状总览

这个赛道的产品可以分成三类，**彼此很少打通**：

| 类型 | 代表产品 | 解决什么 | 普遍缺失 |
|---|---|---|---|
| A. 随机决策类 | 吃啥呢吃、随便·都可以·食、美食大转盘 | 快速决定「吃什么」 | 记录很弱，多止于一条历史流水 |
| B. 菜谱/点菜类 | 懂你的菜谱、我是大吃货、NiniMenu | 不知道做什么菜、冰箱有什么 | 没有热量闭环，不看长期饮食结构 |
| C. 饮食记录类 | 薄荷健康、MyFitnessPal、千卡记、记一餐 | 记录吃了什么、控卡 | 没有「决策」能力，得先知道吃什么才能记 |

**核心空白：A + C 几乎没有被打通的产品。** 市面上的抽签工具抽完就结束，饮食记录工具又要求你自己先想好吃什么。本项目要做的「抽签 → 记入三餐 → 月历回看 → 热量复盘」正好是这条断层，这是最大的差异化机会。

## 二、逐个产品拆解

### 1. 吃啥呢吃（微信小程序）
- **玩法**：转盘 / 盲盒 / 抽签桶 / 老虎机 / 翻牌 / 跑马灯，6 种随机方式；转盘默认解锁，其余靠分享解锁。
- **其他**：拍照识别食材 → AI 推荐菜谱；「附近」定位推荐周边商家；历史记录可一键复用；生成分享海报。
- **可借鉴**：① 多种随机玩法是留存钩子，但 v1 只需 1–2 种；② 「历史记录一键复用」很实用（再吃一次）；③ 分享海报/分享解锁是增长手段。
- **不足**：无热量、无日历、无菜系维度；玩法数量 > 功能深度。

### 2. 我是大吃货 / 阿卉大食堂（微信小程序）
- **玩法**：点菜面板（荤菜/素菜/主食/凉拌菜/汤品，22 道家常硬菜）、2 人餐模式、随机点菜、创建点菜房间多人协作。
- **其他**：拍照识菜（**输出含热量，如「蒜蓉西兰花 95 大卡」**）、烹饪计时器、食材保鲜百科、收支记账（月开销柱状图）、积分签到。
- **可借鉴**：① **菜品直接带热量**是这个方向最直接的验证；② 按「荤/素/主食/汤」结构化，天然适合做营养均衡校验；③ 花费统计同理可迁移为热量统计。
- **不足**：无菜系维度（只有菜品分类）；记账靠手动，不是决策闭环。

### 3. 随便·都可以·食（搬砖的猫，小程序 + 网页 hataraku-neko.cn）
- **玩法**：随机点名 / 幸运转盘 / 多人投票。
- **其他**：**决策记录 + 数据分析**——「月底一看：原来你吃了 12 次麻辣烫」。三只折纸猫 IP，极简设计。
- **可借鉴**：① **把记录做成洞察（频次统计 + 一句话吐槽）**，这是本产品统计页的模板；② 极简视觉 + IP 人格化，成本低但记忆点强。
- **不足**：只有一条流水，没有早/中/晚结构化，也没有热量。

### 4. 懂你的菜谱（微信小程序）
- **玩法**：随机推荐换一批、关键词搜索（支持搜「空气炸锅」「电饭煲」等炊具）、冰箱点名（报食材 → 组合出菜）、签筒抽签、分类点菜（早餐/午餐/晚餐/夜宵/减脂/家常菜/下饭菜/快手菜…）。
- **其他**：收藏、**花费记录（按天/月统计，月合计 ¥109）**。
- **可借鉴**：① 「早餐/午餐/晚餐/夜宵」分类 + 场景标签（减脂、下饭、快手）非常贴合本项目；② **日历式的按天/月统计视图**几乎是本产品月历的现成参考。
- **不足**：热量缺失；记录的是花费不是营养。

### 5. 今天吃什么（App，iOS/Android）
- **玩法**：趣味抽签 / 转盘 / 九宫格；自定义录入家常菜、外卖、门店清单；**忌口黑名单自动过滤**；输入冰箱食材匹配快手食谱；用餐记录；云端保存。
- **可借鉴**：**忌口/黑名单过滤**是刚需（不吃香菜、不吃辣、过敏），必须进 v1 或 v1.1。
- **不足**：评论区反映广告与功能堆砌。

### 6. NiniMenu（开源 Web，Go + TypeScript，143 star）
- **规模**：632 道菜，**按菜系分类**——家常菜 48 / 川菜 73 / 粤菜 51 / 湘菜 97 / 东北菜 44 / 新疆菜 32 / 云南菜 56 / 贵州菜 71；另有「酸/甜/辣/鲜/清淡」口味筛选。
- **玩法**：智能推荐（基于历史偏好）/ 心情匹配 / 转盘抽奖 / 盲盒；收藏夹智能分组；**自动生成 7 天周计划**；购物清单；80+ 成就系统；烹饪模式；记录页 + 照片墙。
- **可借鉴**：① **菜系作为一等分类维度已被验证**（且给出了各菜系的合理菜品量级：30–100 道）；② 口味维度（酸甜辣鲜清淡）比菜系更低门槛；③ 记录页按天分组 + 照片墙的呈现方式。
- **不足**：全栈项目重，需部署后端；无热量；无月历视图。

### 7. 开源纯前端转盘类（what-to-eat / 美食大转盘 / FoodWheel）
- **共性**：纯 HTML+CSS+JS、Canvas 绘制转盘、分类切换（午餐/晚餐/饮品/零食）、历史记录、烟花/彩带特效、GitHub Pages 托管、手机适配。
- **技术细节值得抄**：转盘至少转 5 圈 + ease-out 减速、指针精准对齐、结果卡弹出、Web Audio 合成音效（无需音频文件）、localStorage 保存自定义菜单。
- **不足**：菜品是硬编码的十几条，没有数据体系；无记录/无热量。
- **结论**：这类项目证明了**纯前端 + GitHub Pages 的技术路线完全可行且足够**，我们的差距不在技术上，而在数据体系和记录闭环。

### 8. 饮食记录类（薄荷健康 / MyFitnessPal / 千卡记 / 记一餐）
- **共性**：百万级食物数据库、拍照或扫码识别、三餐打卡、**日历贴纸视图**、每日热量汇总、体重曲线。
- **可借鉴**：① 日历 + 贴纸是「记录可视化」的最优形态；② 每日热量用进度环呈现；③ 记录速度是留存生命线（行业数据：单条记录超过 30 秒就会被放弃）。
- **对本项目的关键启示**：本产品的热量是**「估算值」而非「精确值」**，必须 ① 明确标注估算；② 记录要做到「一键写入」，绝不能让用户手填克数，否则会重蹈饮食记录 App 的流失覆辙。

## 三、结论与差异化定位

### 3.1 市场验证过的要素（照做）
1. 转盘/抽签是标配，纯前端实现成熟（Canvas + CSS 动画 + localStorage）。
2. **菜系分类有人做过（NiniMenu）且量级合理**：单菜系 30–100 道。
3. **菜品直接带热量有人做过（我是大吃货）**，用户接受度高。
4. **按天/月的记录统计视图有人做过（懂你的菜谱）**，形态可参考。
5. 忌口黑名单、收藏、「再吃一次」是刚需细节。

### 3.2 市场没做好的（我们做）
| 差异点 | 说明 |
|---|---|
| **决策 → 记录闭环** | 抽中即一键写入当天对应餐次，零手填。市面产品要么只抽不记，要么只记不抽。 |
| **早/中/晚结构化 + 月历** | 市面「今天吃什么」几乎都没有餐次维度；饮食记录类有餐次但没决策。本项目把两者绑在一起。 |
| **菜系 + 口味双维度** | 菜系负责「大方向」，口味/场景（快手、下饭、减脂、清淡）负责「当下心情」，比单一维度更好用。 |
| **热量复盘而非热量记账** | 不追求精确到克，给「本月日均热量、三餐配比、菜系分布」的趋势洞察，配免责声明。 |
| **纯前端、数据本地** | 无账号、无上传、可离线，隐私零顾虑，也符合无后端成本的前提。 |

### 3.3 风险提示
- 功能面铺得太宽（抽签+菜库+日历+热量+统计）容易做成四个半成品。**v1 必须克制**：核心路径只有一条——「抽 → 记 → 看」。
- 热量数据的准确性是信任底线，宁可粗（区间）也不要装精确。
