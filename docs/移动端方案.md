# 「今天吃什么」跨平台移动应用方案（v1.0）

> 评审用方案 + 移动端原型。日期：2026-09-20　面向平台：iOS 15+ / Android 8.0+（API 26+）
> 结论先行：**不重写、不引入原生外壳**，用「同一套 React 代码 + PWA + 移动端体验重做」跨双端。理由见 §2。

---

## 1. 现状体检（基于当前线上版实测）

在生产构建（`dist/`）上以 iPhone 14 逻辑分辨率 390×844 实测，得到以下硬数据：

| 指标 | 实测值 | 判断 |
|---|---|---|
| JS 产物（gzip 后） | **83.7 KB** | ✅ 优秀，同类应用常见 150–300 KB |
| CSS 产物（gzip 后） | **3.2 KB** | ✅ 优秀 |
| logo.png | **243 KB** | ❌ **单文件占全站 74%**，且 500×500 原图缩到 48px 显示 |
| 生产 JS 原始体积 | 268 KB | ✅ 合理（React 19 + 业务） |
| 菜库 | 160 道，20 KB 源码 | ✅ 体积无压力，可扩到 400 道不影响加载 |

**结论：性能不是瓶颈，真正的问题在「移动端交互」和「原生质感」。**

### 1.1 实测发现的移动端体验问题

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| P1 | **顶栏右侧文字被裁切** | 「不知道吃什么就交给它 · 9…」在 390px 下溢出 | 首屏就有破损感，最伤第一印象 |
| P2 | **页面纵向过长，核心 CTA 沉底** | 餐次+菜系+筛选按钮+「当前…」+转盘+按钮 = 约 3 屏；「今天吃什么」按钮在首屏之下 | 用户要多滑一次才能完成核心动作，与 PRD「≤3 次点击、三秒出结果」冲突 |
| P3 | **筛选区与转盘争夺首屏** | 菜系 12 个 chip 横向滚动，必须滑 4 屏才能看完 | 横向滚动手势与转盘/滑动切换冲突 |
| P4 | **筛选状态无法感知** | 滑到转盘时已看不见「当前：…」，不知道自己筛了什么 | 抽出不想要的结果时才会发现 |
| P5 | **结果卡用居中模态遮挡转盘** | `rmask` 全屏遮罩 + 居中卡片 | 断掉了「转盘→结果」的连续心理动线，像弹出广告 |
| P6 | **夜宵仅 18 道候选** | 早餐 41 / 午餐 136 / 晚餐 128 / 夜宵 18 | 夜宵连抽几次就重复，体验塌陷 |
| P7 | **一处穿帮菜** | 「水煮蛋」食材写成「鸡蛋。火腿丁、葱花」 | 数据录入错误，影响信任 |
| P8 | **无 PWA 能力** | 无 manifest / service worker | 无法「添加到主屏幕」、无离线、无启动图标 |
| P9 | **无任何触感与手势** | 无 `navigator.vibrate`、无滑动切换、无下拉 | 像网页不像 App |
| P10 | **无安全区适配验证** | index.html 已加 `viewport-fit=cover`，但未实测 iOS 刘海/Home 条 | iPhone 15 等机型可能被遮挡 |

## 2. 技术路线：为什么不重写

| 方案 | 说明 | 判断 |
|---|---|---|
| **A. React Native / Expo 重写** | 原生质感最好，可上架 App Store | ❌ 需重写全部 4 个页面 + 160 道菜库 + 51 项测试；双端原生模块（振动/通知）要各自实现；发版要过审。**成本约为 B 的 4–6 倍，收益仅「上架」一项** |
| **B. Flutter 重写** | 性能与一致性最好 | ❌ 同上，且团队栈是 React/TS，迁移等于换团队能力 |
| **C. Capacitor / Cordova 套壳** | 复用现有代码，得到 ipa/apk | ⚠️ **比 A 便宜，但比 B 更贵**：仍需 Apple 开发者账号（$99/年）+ 双端签名流水线 + 提审；且内核仍是 WebView，没有比 PWA 更好的移动体验 |
| **D. PWA + 移动端体验重做**（推荐） | 现有 React 代码直接复用，加 manifest + service worker，**把移动端布局按原生习惯重排** | ✅ **推荐**。0 重写、0 审核、0 签名成本，iOS/Android 都能「添加到主屏幕」并获得独立图标 + 全屏 + 离线 |
| **E. 微信小程序** | 国内触达最快 | ⚠️ 需重写（WXML 另一套语法），且不能复用现有 store/lib 口径。**可作为 v2 的渠道扩展，不作为跨平台主线** |

**决策：走 D。** 关键判断是——本产品的核心动作是「抽一个结果 + 记一条记录」，**没有任何一处依赖原生能力**（无摄像头、无 GPS、无推送、无支付、无后台定位）。为了「能上架」而重写 4 个页面，投入产出比极差。

**什么时候才该转向 A/C：** 当出现以下任一需求时——
1. 需要推送通知（饭点提醒「该决定今天吃什么了」）——这是唯一真正需要原生的场景；
2. 需要上架以获取应用商店流量；
3. 需要读取健康数据（同步热量到 Apple Health / 华为运动健康）。

> 若第 1 条成为刚需，建议路径是 **D → Capacitor 套壳（仅补推送插件）**，而不是重写 UI。

## 3. 移动端体验重做（核心交付）

### 3.1 布局重构：从「纵向堆叠」到「一屏闭环」

现状是桌面布局在小屏上等比堆叠，导致 3 屏。改造原则：

| 区域 | 现状 | 改造后 |
|---|---|---|
| 顶部 | h1 + 被裁切的副标题 | **紧凑顶栏**：只留「抽签」+ 日期；副标题移到空态提示里 |
| 餐次切换 | 卡片 + 下方解释文字 | **分段控件（Segmented Control）**，吸顶，去掉解释文字 |
| 菜系筛选 | 12 个 chip 横向滚动 | **移入底部抽屉**，首屏只留一个「筛选」按钮 + 已选条件 chip（可一键移除） |
| 玩法切换 | 「转盘/抽签桶」按钮挤在筛选行 | 并入顶部插件式图标按钮 |
| 主区 | 转盘 300px + 独立卡片 | **转盘占满剩余高度**，随屏自适应 |
| 主 CTA | 卡片内按钮，需下滑 | **固定底部悬浮按钮（FAB 式）**，永远可见 |
| 结果 | 居中模态遮罩 | **底部 Sheet 从下方推入**，转盘仍露出一半，动线连续 |

**收益：核心动作从「滑动 + 点击」变成「点一下 CTA」，真正达到 PRD 要求的三秒出结果。**

### 3.2 逐项体验优化

**① 触觉反馈（Haptic）**
- 转盘旋转：每经过一个扇区边界 `navigator.vibrate(8)`（Android 有效，iOS 静默降级）
- 出结果瞬间：`navigator.vibrate([0, 30, 40, 60])` 双震，模拟「抽出」的确认感
- CTA 点击：`vibrate(12)`
- 全部走一个 `lib/haptics.ts` 封装，**无 API 时静默**，不影响任何逻辑

**② 手势**
- 主区**左右滑动切换餐次**（早→午→晚），符合原生 Tab 直觉
- 结果 Sheet **下拉关闭**（拖过 30% 高度即关闭，带阻尼）
- 底栏上滑隐藏、下拉显示（仅抽签页，给转盘让出高度）

**③ 视觉与动效（对齐 iOS HIG / Material 3 的通用最小集）**
- **点击态压缩**：所有可点元素 `active` 时 `scale(0.97)`，200ms —— 这是"像 App"最关键的一招
- **触控热区 ≥ 44×44 pt**（现状 `btn-sm` 只有 32px 高，`chip` 34px，均不达标）
- **转盘改为结果优先**：抽中后扇区保持高亮 400ms 再推入结果 Sheet
- **尊重系统「减弱动态效果」**：`prefers-reduced-motion` 时转盘只转 1 圈
- 暗色模式**跟随系统**（现状默认浅色 `theme: 'light'`，应改为 `'auto'`）

**④ 空态与错误态**
- 筛选过窄无候选时：不显示空转盘，改为「没有符合条件的菜」+ 一键放宽筛选
- 无本地数据时：当前用固定种子生成示例数据 —— 移动端应改为**明确的空态引导**，示例数据只放在设置里「载入示例」按钮

**⑤ 首屏加载**
- 骨架屏：转盘位置先渲染灰环，避免布局跳动（CLS）
- logo 压缩：243 KB → **≤ 12 KB**（webp/avif + 正确的 48/96/192/512 多尺寸），可选改成内联 SVG
- 预连接：无外链，无需处理

## 4. PWA 配置规格（跨双端的必要件）

| 文件/项 | 要求 | 备注 |
|---|---|---|
| `manifest.webmanifest` | `name` / `short_name`（今天吃什么）/ `display: standalone` / `orientation: portrait` / `theme_color: #1C1917`（暗色优先）/ `background_color: #1C1917` | 暗色优先与 PRD §6.2 一致 |
| 图标 | 192×192 + 512×512 + **512 maskable**（Android 自适应）+ `apple-touch-icon` 180×180 | maskable 需留 20% 安全边距，否则被裁成圆角后缺角 |
| Service Worker | `vite-plugin-pwa`，`registerType: 'autoUpdate'`，预缓存全部静态资源 | 菜库是编译进 JS 的，缓存后**完全离线可用** |
| 导航兜底 | SW 用 `navigateFallback` 处理，注意 `base: '/what-to-eat/'` 子路径 | 现有 vite base 已配置，需保持一致 |
| iOS 适配 | `apple-mobile-web-app-capable`（已有）+ `apple-mobile-web-app-status-bar-style` 改为 `black-translucent` | 实现全屏沉浸 |
| 安全区 | `padding: env(safe-area-inset-*)`，底部 CTA 必须加 `safe-area-inset-bottom` | 现有 tabbar 已加，FAB 需同步 |

**更新策略**：`autoUpdate` + 设置页显示「有新版本，点击刷新」，避免用户长期停留在旧缓存版本（纯前端应用最容易被这个坑到）。

## 5. 数据与状态层（复用，零改动）

现有分层已经非常适合移动端，**不需要任何重构**：

```
data（160 道菜库/元数据/种子）
  → lib（纯函数：date / pool / stats / storage）  ← 口径单一来源，可直接复用
  → stores（zustand 单 store）
  → components / pages
```

| 关注点 | 现状 | 移动端调整 |
|---|---|---|
| 持久化 | localStorage，前缀 `wte:v1:` | ✅ 直接复用。iOS Safari 在存储压力下可能清理 localStorage，**建议补 navigator.storage.persist() 申请持久化**；若仍担心，v2 迁 Dexie/IndexedDB |
| 统计口径 | `lib/stats.ts` 唯一来源 | ✅ 零改动 |
| 抽取口径 | `lib/pool.ts` 唯一来源 | ⚠️ 建议补一条**移动端专属权重**：夜宵候选仅 18 道，7 天降权后容易重复，建议夜宵档位把「7 天」放宽到「3 天」 |
| 状态管理 | zustand 单 store | ✅ 零改动 |
| 测试 | 51 项 vitest | ✅ 直接复用；新增的 `haptics` / 手势需补单测 |

## 6. 性能目标与实测基线

| 指标 | 目标 | 当前 |
|---|---|---|
| 首屏可交互（4G，中端机） | ≤ 1.5s | 未实测，产物 84 KB 预估可达 |

| 阶段 | 范围 | 影响面 |

## 8. 验收标准（移动端）

1. iPhone SE(375) / iPhone 14(390) / Pixel 7(412) 三档下**无横向滚动、无文字裁切**。
2. 首屏**不滑动即可点到「今天吃什么」**；从启动到出结果 ≤ 3 次点击。
3. 所有可点元素**实测命中区 ≥ 44×44 px**（含 chip、关闭按钮、tab）。
4. 转盘→结果→记入全程**无全屏遮挡**，动线连续。
5. 在 iOS Safari 与 Android Chrome 上「添加到主屏幕」后：**独立图标、全屏无地址栏、断网可用**。
6. 呼吸/Safe Area 机型下，底部 CTA 与 tab 不被手势条遮挡。
7. 数据写满 1000 条记录后，日历与统计页滚动仍 ≥ 50 fps。
8. 亮/暗两种系统主题下均无对比度问题（WCAG AA）。

## 9. 风险

| 风险 | 应对 |
|---|---|
| iOS 对 PWA 支持弱于 Android（无推送、后台受限） | 本产品不依赖推送，无影响；若将来要推送，走 §2 的 M4 套壳路径 |
| iOS Safari 可能清理 localStorage | 申请 `storage.persist()` + 保留导出备份 + 引导用户定期导出 |
| 「添加到主屏幕」需用户手动操作，安装率低 | 首屏底部加一条可关闭的引导条；不做强制弹窗 |
| 横向滚动的菜系 chip 与滑动手势冲突 | 菜系筛选移入抽屉后此冲突自然消失 |
| 底部 Sheet 在 Android WebView 上的键盘顶起问题 | 补录搜索框聚焦时切换为全屏 Sheet |
